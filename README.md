# Project Osmos demo in Microsoft Fabric

[Wersja polska](README.pl.md)

Raw retail sales files from which an agent builds a medallion architecture.

This repository describes a sample workspace for showing Project Osmos in practice. The Lakehouse holds raw CSV files from a fictional store chain. The files are deliberately dirty, because that is where you can see the agent explore the data on its own, write and run Spark code, fix it after errors, and leave notebooks and Delta tables behind.

The Osmos task has not been run yet. Everything is prepared so that it can be started live during a presentation.

## What Project Osmos is

According to the product description shipped with the `project-osmos` skill (Microsoft Skills for Fabric), it is a long-running data engineering agent for Fabric. It receives a description of the expected outcome rather than a list of steps. It can explore data, write and run Spark code, create and test notebooks, clean and transform data, and create or update Delta tables. The whole run is a single task visible in the Fabric portal. When in doubt, it can stop and ask a question.

The Lakehouse selected when the task starts is only used to start a Spark session in the right workspace and on its capacity. It does not limit what the agent can read or where it writes results.

Starting Osmos from the Copilot built into the Fabric portal is not supported at the moment. The task is started from a local agent, for example GitHub Copilot CLI with the `fabric-skills@fabric-collection` package installed.

| Tenant | test tenant with a Fabric capacity (`<tenant>`) |

Contents of `Files/raw/retail/` after upload (checked with an OneLake DFS listing):

| File | Rows | Size | Notes |
|---|---|---|---|
| `stores.csv` | 12 | 533 B | 11 physical stores and 1 online channel |
| `customers.csv` | 2 040 | 154 491 B | comma separator |
| `products.csv` | 300 | 13 774 B | semicolon separator |
| `orders/orders_part1.csv` | 25 125 | 1 543 026 B | orders from 1 Nov 2024 to 31 Oct 2026 |
| `orders/orders_part2.csv` | 25 125 | 1 543 046 B | second part of the same export |

All data is synthetic, generated by a script with a fixed random seed. It contains no customer data of any kind. Column values (city names, segment names, product categories) are in Polish.

## Injected data quality issues

The script counted every issue it introduced. These numbers let you check after the task finishes whether Osmos caught everything, instead of taking its word for it.

| Issue | Count |
|---|---|
| customers: duplicated row | 40 |
| customers: empty city | 40 |
| customers: upper-case e-mail | 38 |
| customers: lower-case segment or trailing space | 78 |
| products: price with decimal comma | 17 |
| orders: duplicated order (identical row) | 250 |
| orders: date as DD.MM.YYYY instead of ISO | 2 042 |
| orders: missing customer_id | 532 |
| orders: customer_id not in the customer list | 242 |
| orders: negative quantity | 521 |

Source: `dane/wstrzykniete_problemy.csv` (issue names in Polish). Several issues can hit the same row (for example a duplicated order with a Polish-format date), so the totals should not be compared one-to-one with the number of rejected records.

On top of that, the products file uses a different separator than the other files, and orders are split into two files. The agent has to notice this by itself, because the prompt does not mention it.

## Prompt

The prompt is in `prompt_osmos.txt`, written in Polish. It deliberately describes the outcome rather than how to get there. An English translation for reference:

```text
In Lakehouse lh_retail, the folder Files/raw/retail contains raw CSV exports
from a store chain: customers.csv, products.csv, stores.csv and orders in the
orders/ folder. Build a medallion architecture from them.

Bronze: load the files without changing their content into Delta tables
bronze_customers, bronze_products, bronze_stores and bronze_orders, adding
columns with the source file name and load time.

Silver: clean and standardise the data. Remove duplicates, standardise date,
number, e-mail and segment name formats, assign correct types. Records that
cannot be fixed (e.g. orders without a customer, with an unknown customer or
with a negative quantity) should go to a silver_rejected_orders table with a
column describing the rejection reason, instead of being silently deleted.

Gold: create gold_monthly_sales (month, product category, customer segment,
store city, channel, order count, quantity, net revenue after discount,
completed status only) and gold_customer_360 (customer, segment, first and
last order, order count, net revenue, return share).

For each layer prepare a separate, tested notebook saved in the workspace, so
that the whole thing can be rerun without duplicating data. At the end report
the row count of every table, the number of rejected orders by reason and the
number of fixed records by issue type.
```

## Running the demo

1. In GitHub Copilot CLI, signed in (`az login`) to your tenant, ask it to use Project Osmos with the prompt from `prompt_osmos.txt` on workspace Osmos-Demo and Lakehouse lh_retail.
2. The skill runs a short interview about task settings: what the agent may change, how it should behave on rerun, whether it may change schemas, and what reasoning level to use. For this demo it is reasonable to allow creating new tables and notebooks in `Osmos-Demo` without permission to change other workspaces.
3. After the start, the CLI prints a task card with a link to the task page in the Fabric portal. Show that page on screen, because it lists the agent's steps, code and query results.
4. You can check progress by asking the CLI for the task status. If Osmos asks a question, the answer goes back to the same task. No new task is created.
5. When the task finishes, the workspace should contain notebooks and `bronze_*`, `silver_*`, `gold_*` tables. Compare the results with the injected issues table above.

Task duration and F8 capacity consumption have not been measured, because the task has not been run yet. Do a dry run before showing it to a customer.

## What to show the audience

The most interesting moments are when the agent hits a problem the prompt does not describe: the semicolon in `products.csv`, two date formats, or customers missing from the customer list. Ask the audience how they would solve it, then show what Osmos did.

The second strong point is accountability. The numbers in the final report can be compared with `wstrzykniete_problemy.csv`. If something does not match, it is a good opening to talk about checking an agent's output the same way you would check a person's work.

## Recreating the environment

Scripts are in `metodyka/`.

```powershell
cd metodyka
python generuj_dane.py          # data to ..\dane\raw, fixed seed
.\przygotuj_workspace.ps1 -CapacityName <capacity-name>   # workspace, lakehouse, upload to OneLake
```

`przygotuj_workspace.ps1` is idempotent for the workspace and the Lakehouse: if they already exist, it reuses them. Files are overwritten. The `-WorkspaceName`, `-CapacityName` and `-LakehouseName` parameters let you deploy a copy elsewhere. The script looks up the capacity by name, so set `-CapacityName` to a capacity you have access to.

The script prints the workspace ID at the end. Delete the workspace with:

```powershell
az rest --method delete --url https://api.fabric.microsoft.com/v1/workspaces/<workspace-id> --resource https://api.fabric.microsoft.com
```

## Open questions

- It has not been checked whether Project Osmos is enabled in the test tenant. This will only show up on the first attempt to create a task.
- It is not known how long the task will take or how many CUs it will use on F8.
- Notebook names and their split are chosen by the agent. The prompt asks for one notebook per layer, but the final shape depends on Osmos.
- The description of Osmos capabilities comes from the skill documentation, not from Microsoft Learn. Before showing it to a customer, check the current product status (preview, regional availability).
